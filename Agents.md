# Правила для агента (Quest Mode)

## Золотое правило

ЗАПРЕЩЕНО писать код до утверждения спецификации. Спецификацию нужно сохранить в файле для утверждения.

## Обязательный процесс

1. Фаза SPEC:
   - Задать уточняющие вопросы, если есть неопределённость
   - Сформировать спецификацию в каталоге /specs
   - Использовать шаблон /specs/_template.md
   - Выбрать профиль из .codex/profiles
2. Quality gate:
   - Прогнать SPEC-LINTER.md (самопроверка)
   - Если линтер выявил недостатки, агент ОБЯЗАН вернуться на фазу SPEC и задать уточняющие вопросы
   - Если спецификация набирает менее 21 балла по SPEC-RUBRIC, агент ОБЯЗАН явно указать, что автономное выполнение рискованно, объяснить почему и предложить варианты снижения рисков
   - Если проверки качества прошли успешно, запросить подтверждение фразой: "Спеку подтверждаю"
   - НЕ переходить к реализации без явного подтверждения пользователя
3. Фаза EXECUTION:
   - Только после подтверждения
   - Реализовать строго по спецификации
   - Соблюдать Non-Goals и ограничения
   - Выполнить тесты и команды из спеки
   - Выдать итоговый отчёт

## Источники истины

- Процесс: .codex/QUEST.md
- Профили: .codex/profiles/*
- Линтер: .codex/lint/SPEC-LINTER.md

# Общие правила взаимодействия с агентом

## Языковые предпочтения

1. Все общение должно вестись на русском языке
2. Вся документация, комментарии и пояснения должны быть на русском языке
3. Технические термины могут сохраняться в оригинальном виде (например, "ASP.NET Core", "xUnit")

## Основные принципы работы

1. При решении задач необходимо:
   - Подробно объяснять каждый шаг
   - Предоставлять контекст и причины принимаемых решений
   - Предложить несколько вариантов решения, обосновать сильные и слабые стороны каждого и дождаться явного выбора от пользователя
   - Проверять работу кода перед завершением задачи
2. При работе с кодом:
   - Использовать только существующие файлы проекта
   - Не создавать новые файлы без явной необходимости
   - Сохранять структуру и стиль кода проекта
3. При создании или изменении файлов:
   - Все комментарии должны быть на русском языке
   - Названия переменных и функций могут оставаться на английском
   - Документация к функциям и классам должна быть на русском

## Стиль общения

1. Отвечать чётко и по делу
2. Избегать излишне формального тона
3. Объяснять технические моменты доступным языком
4. Предлагать альтернативные решения при необходимости

## Работа с ошибками

1. При обнаружении ошибок:
   - Подробно описать проблему
   - Предложить несколько вариантов решения
   - Объяснить последствия каждого варианта
   - Написать тест для воспроизведения перед исправлением, чтобы проверить, что ошибка ушла, и чтобы её возвращение в будущем фиксировалось падением теста
   - Запускать тесты и исправлять, пока тест не будет проходить
2. При тестировании:
   - Проверять работоспособность внесённых изменений
   - Если тест упал, нужно определить, это проблема в тесте или в логике. Если вероятно и то и другое, спросить у меня, чтобы я принял решение
   - Указывать, как протестировать функциональность

## Автоматическое тестирование

### Обязательное покрытие тестами

**КРИТИЧЕСКИ ВАЖНО:** Любые изменения в коде ДОЛЖНЫ сопровождаться автоматическими тестами.
**Требование:** Перед завершением задачи должны быть запущены все тестовые проекты. В процессе разработки допускается запуск только тех тестов, которые затрагиваются изменениями.

### 1. При добавлении новых функций

**Обязательно:**

- Написать unit-тесты для всех новых функций и методов (xUnit)
- Покрыть все ветки логики (if/else, switch, циклы)
- Протестировать граничные случаи и edge cases

**Порядок действий:**

1. Реализовать функцию
2. Написать тесты, покрывающие:
   - Успешные сценарии (happy path)
   - Граничные значения (пустые строки, null, 0, отрицательные числа)
   - Ошибочные входные данные
   - Edge cases специфичные для функции
3. Запустить тесты: `dotnet test`
4. Убедиться, что все тесты проходят

**Пример (xUnit):**

```csharp
using Xunit;

public class PlannedDatesHelperTests
{
    [Fact]
    public void ShouldThrowWhenDateIsInPast()
    {
        var date = DateTimeOffset.Now.AddDays(-1);
        Assert.Throws<BusinessException>(() => PlannedDatesHelper.ValidatePlannedDate(date));
    }
}
```

### 2. При исправлении багов

**ОБЯЗАТЕЛЬНЫЙ алгоритм TDD (Test-Driven Debug):**

1. **Написать failing тест** - создать тест, воспроизводящий баг

   ```csharp
   [Fact]
   public void Bug_DivideByZero_ShouldThrow()
   {
       Assert.Throws<DivideByZeroException>(() => Calculator.Divide(5, 0));
   }
   ```

2. **Запустить тест** - убедиться, что тест падает (воспроизводит баг)

   ```bash
   dotnet test src/UTEP.Tests/UTEP.Tests.csproj --filter Bug_DivideByZero_ShouldThrow
   ```

3. **Исправить код** - внести минимальные изменения для исправления
4. **Запустить тест снова** - убедиться, что тест теперь проходит
5. **Запустить все тесты** - проверить, что исправление не сломало другую функциональность

   ```bash
   dotnet test
   ```

**Важно:** Тест должен остаться в кодовой базе как regression test, чтобы предотвратить возврат бага.

### 3. При изменении существующей функциональности

**Обязательно:**

- Обновить существующие тесты, если меняется поведение
- Добавить новые тесты для нового поведения
- Запустить все тесты перед и после изменений

**Порядок действий:**

1. Запустить существующие тесты: `dotnet test`
2. Внести изменения в код
3. Обновить/добавить тесты
4. Запустить тесты снова

### 4. Типы тестов в проекте

#### Unit-тесты (xUnit)

**Где:**

- `src/UTEP.Tests/UTEP.Tests.csproj`

**Когда использовать:**

- Тестирование отдельных функций и модулей
- Проверка бизнес-логики и правил валидации
- Тестирование утилит и хелперов

**Команды:**

```bash
dotnet test
dotnet test src/UTEP.Tests/UTEP.Tests.csproj
```

**Стандарты:**

- Все публичные функции должны быть покрыты
- Тесты должны быть независимыми друг от друга
- Использовать `[Fact]`/`[Theory]` для структурирования

### 5. Проверка перед коммитом

**ОБЯЗАТЕЛЬНЫЙ чеклист перед каждым коммитом:**

```bash
# 1. Форматирование кода
dotnet format

# 2. Сборка как статическая проверка
dotnet build

# 3. Запуск всех тестов
dotnet test
```

**Все должно быть зелёным перед коммитом!**

### 6. Примеры тестирования разных сценариев

#### Тестирование функции с side-эффектами

```csharp
[Fact]
public void UpdateExpression_ShouldChangeState()
{
    var state = new State { Expression = "x + 1" };
    ExpressionUpdater.UpdateExpression(state, "x + 2");
    Assert.Equal("x + 2", state.Expression);
}
```

#### Тестирование асинхронного кода

```csharp
[Fact]
public async Task LoadData_ShouldReturnData()
{
    var data = await DataLoader.LoadAsync();
    Assert.NotNull(data);
}
```

#### Тестирование исключений

```csharp
[Fact]
public void Parse_ShouldThrowOnInvalidInput()
{
    Assert.Throws<ParseException>(() => Parser.Parse("invalid"));
}
```

### 7. Когда можно НЕ писать тесты

**Исключения (очень редкие случаи):**

- Чисто документальные правки без изменения логики
- Временные экспериментальные скрипты
- Прототипирование (но перед мержем в main - тесты обязательны)

**ВО ВСЕХ ОСТАЛЬНЫХ СЛУЧАЯХ ТЕСТЫ ОБЯЗАТЕЛЬНЫ.**

### 8. Отладка падающих тестов

**Если тест упал:**

1. Прочитать сообщение об ошибке
2. Запустить только этот тест:

   ```bash
   dotnet test src/UTEP.Tests/UTEP.Tests.csproj --filter ИмяТеста
   ```

3. Добавить логирование для промежуточных значений
4. Использовать отладчик и breakpoint
5. Проверить assumptions

### 9. Continuous Integration

**При работе с CI/CD:**

- Все тесты должны проходить на CI
- Не мержить PR если тесты красные
- Если тест нестабильный (flaky) - исправить или удалить

### 10. Культура тестирования

**Правила команды:**

- Код без тестов = незавершённый код
- Failing тест важнее чем его отсутствие
- Тесты - это документация того, как код должен работать
- Хороший тест проваливается когда код сломан, и проходит когда код работает
- Тесты должны быть простыми и понятными
- Один тест = одна проверка (один assert в идеале)

## Дополнительные правила

1. Стек проекта: .NET 8, C#.
2. Публичный API не менять без явного согласования; любые изменения фиксировать в спеках.
3. Все создаваемые диаграммы должны быть без стилей и оформления.
4. При генерации кода обеспечивать его немедленную работоспособность.
