# Спецификация: UTEP CLI v1.1 (dotnet tool)

## 1. Цель
- Реализовать CLI‑инструмент UTEP как `dotnet tool` по спецификации v1.1 (`UTEP-SCHEMA.md`) с парсингом команд через `System.CommandLine` и human‑выводом через `Spectre.Console` (только рендер, без `Spectre.Console.Cli`).
- Обновить `UTEP-SPEC.md` до актуального уровня v1.1, чтобы он соответствовал `UTEP-SCHEMA.md`.

## 2. Текущее состояние (AS-IS)
- В репозитории есть документация (`UTEP-SPEC.md`, `UTEP-SCHEMA.md`, `README.md`, `AGENT-RUNBOOK.md`), но нет исходников CLI.
- `UTEP-SPEC.md` описывает более раннюю версию (v1.0) и расходится с детальным контрактом v1.1 в `UTEP-SCHEMA.md`.

## 3. Проблема
- Отсутствует рабочий CLI, поэтому протокол нельзя применять.
- Спецификация v1.0 и детальная схема v1.1 расходятся, из-за чего нет единого источника истины.

## 4. Целевое состояние (TO-BE)
- Реализован `dotnet tool` UTEP с командами и JSON‑envelope, строго по `UTEP-SCHEMA.md`.
- Человеческий вывод (`human`) оформлен через `Spectre.Console`.
- Парсинг команд и опций выполняет `System.CommandLine`.
- Репозиторий имеет структуру `src/UTEP.Cli` и `tests/UTEP.Tests`.
- `UTEP-SPEC.md` обновлён и синхронизирован с v1.1.

## 5. Non-Goals
- UI/GUI или web‑интерфейс.
- Хранение данных вне файловой системы.
- Изменение публичного API без явного описания в спеках.
- Поддержка YAML или других форматов файлов.
- Использование `Spectre.Console.Cli` для парсинга команд.

## 6. Области ответственности
- `src/UTEP.Cli/Program.cs` -> входная точка, регистрация команд `System.CommandLine`.
- `src/UTEP.Cli/Commands/*` -> реализация команд и связка с доменными сервисами.
- `src/UTEP.Cli/Domain/*` -> модели, вычисляемые состояния, сортировки, правила.
- `src/UTEP.Cli/IO/*` -> чтение/запись JSON (канонический формат, атомарные записи).
- `src/UTEP.Cli/Services/*` -> `NextSelector`, `BottleneckAnalyzer`, `ValidationService`, `DoctorService`, `RenderService`, `RepoLocator`.
- `tests/UTEP.Tests/*` -> unit‑тесты бизнес‑логики (xUnit).

## 7. Точки интеграции
- Файловая система: `utep.config.json`, `.utep/context.json`, `goals/<id>/*`.
- `dotnet tool` упаковка: корректные параметры `PackAsTool`, `ToolCommandName`.
- Спектр консольного вывода (human), JSON‑ответы в stdout.

## 8. Бизнес-правила (если применимо)
- Логика `next` и сортировка кандидатов: `depth` ↑, `blocks_count` ↓, `priority` ↑, `created_at` ↑.
- `Actionable` только если `Ready` и зависимости сняты.
- `WaitingDependencies` и `needs_review` вычисляемы, в файлы не пишутся.
- Терминальные статусы: `Completed`, `Cancelled`, `Invalidated`.
- `Completed` требует evidence; `Blocked` требует `open_questions`.

## 9. Обработка ошибок
- JSON‑envelope для всех команд в `--json` режиме.
- Коды ошибок: `E400`, `E410`, `E420`, `E430`, `E440`, `E450` по `UTEP-SCHEMA.md`.
- Exit codes: `0` успех, `2` ошибки валидации/нехватка данных, `3` not found/не инициализировано, `4` некорректный переход, `5` empty actionable.
- Degraded mode: `next` и `render` пытаются работать при частичной невалидности.

## 10. Производительность (если применимо)
- Чтение JSON без избыточного парсинга: загрузка только нужных файлов.
- Каноническая запись JSON с минимальным форматированием и атомарной заменой файла.
- Детеминированные сортировки для стабильных выводов.

## 11. Изменения модели данных
- Модель файлов не меняется: JSON v1 уже описан в `UTEP-SCHEMA.md`.
- `UTEP-SPEC.md` обновляется до v1.1 (документация, без изменения структуры файлов).

## 12. План миграции
- Для существующих репозиториев CLI должен читать v1 JSON и корректно работать при отсутствии необязательных полей, используя значения по умолчанию.
- Обновления файлов происходят только через команды CLI (каноническая перезапись).

## 13. Обратная совместимость / откат
- Откат возможен удалением CLI‑инструмента: данные остаются в JSON.
- При записи CLI не изменяет семантику существующих полей.
- Документационное изменение `UTEP-SPEC.md` не влияет на данные.

## 14. Критерии приемки
- [ ] Команды из `UTEP-SCHEMA.md` реализованы и возвращают JSON‑envelope.
- [ ] `utep next` выбирает задачи по правилам сортировки и возвращает `blocking` при пустом пуле.
- [ ] `utep validate` и `utep doctor` формируют issues/remedies как в схеме.
- [ ] `utep render` генерирует `index.md` с маркерами deps/review/blocked и секциями Bottlenecks/Waiting.
- [ ] `UTEP-SPEC.md` синхронизирован с v1.1 (без расхождений с `UTEP-SCHEMA.md`).
- [ ] Тесты xUnit покрывают ключевую бизнес‑логику (next, computed, validation).

## 15. План тестирования и команды
- Тесты:
  - Unit‑тесты `NextSelector` (сортировка, фильтрация `Actionable`).
  - Unit‑тесты вычисляемых состояний (`needs_review`, `waiting_dependencies`).
  - Unit‑тесты `ValidationService` (E001–E005 минимум).
  - Unit‑тесты JSON‑envelope и deterministic sorting.
- Команды:
  - `dotnet build`
  - `dotnet test`
- Результаты SPEC-LINTER:

  - C11 PASS, C12 PASS, C13 PASS
  - D14 PASS, D15 PASS, D16 PASS
  - E17 PASS, E18 PASS, E19 PASS
  - F20 PASS

## 16. Пошаговый план реализации
1. Создать структуру проектов `src/UTEP.Cli`, `tests/UTEP.Tests` и solution, настроить `dotnet tool`.
2. Реализовать доменные модели и вычисляемые состояния, канонический JSON‑IO.
3. Реализовать команды `init/goal/task/next/bottlenecks/validate/doctor/render` по `UTEP-SCHEMA.md`.
4. Добавить `Spectre.Console` для human‑вывода и `System.CommandLine` для парсинга.
5. Обновить `UTEP-SPEC.md` до v1.1.
6. Написать unit‑тесты и прогнать `dotnet build`, `dotnet test`.
